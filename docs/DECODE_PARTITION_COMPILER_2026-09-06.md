# Compiler decode partition/merge

The portable attention optimizer now rewrites a decode online-softmax fold
into a partition map, local folds, and stable ascending softmax-state merge
when the query/batch/head map lacks parallelism. This reuses the prefill
functional representation; model builders do not contain CUDA or model-name
dispatch. Floating-point reduction order changes and is checked numerically,
not assumed bit-identical by an associativity claim.

CUDA lowering implements both direct register and grouped/shared-KV partials.
Decode workspace is indexed by sequence row rather than packed token index.
Empty partitions contribute the identity; the merge touches only decode rows.
The runtime reuses its two-launch executor and deterministic workspace release.
V7 explicitly distinguishes the read-only compiler pair from legacy V3 KV-writing
split kernels. Both partial and merge geometry come from the same portable
strategy planner at startup, not from request-time source inspection.

Initial standalone RTX 5060 Ti / CUDA 13.1 kernel test: 16 query heads, 8 KV heads,
head dimension 128, BF16, 8 partitions. Three schedules are generated by the
same compiler. The old one-CTA grouped schedule is the comparison baseline.

| Context / batch | Baseline µs | Register split-8 µs | Shared-KV split-8 µs |
| --- | ---: | ---: | ---: |
| 59 / 1 | 14.57 | 28.68 | 24.65 |
| 256 / 1 | 51.60 | 49.22 | 26.94 |
| 512 / 1 | 98.23 | 90.11 | 33.14 |
| 1528 / 1 | 285.37 | 251.69 | 57.57 |
| 4096 / 1 | 759.65 | 658.00 | 122.48 |
| 1528 / 8 | 428.95 | 922.96 | 442.47 |

These are initial 200-iteration CUDA-event means, not full-model throughput.
The shared-KV path is selected for small decode batches; short contexts and
larger batches retain the one-kernel path. All nine cases, including context 1
(empty partitions) and mixed prefill/decode rows, matched a stable FP64 CPU
oracle within 0.000477 absolute error, preserved prefill rows and KV bytes,
and released resources. Memcheck/leak check also completed successfully.

## End-to-end Qwen A/B

Completed on the same RTX 5060 Ti, Qwen3-0.6B BF16, identical input token IDs,
fixed output lengths, greedy sampling, c32 deployment capacity and eager
execution. No other GPU workload ran concurrently. Each table value is the
median of three trials: four sequential requests for C1, eight requests for
C8, with warmup before each trial. Rate includes prefill and streaming overhead;
it is not isolated decode throughput. Only LunaFlux was rerun, not competing
frameworks. The baseline already includes the control-reactor progress fix.

The first three C8 differences are approximately noise-level. The split path
is disabled above four active decode rows; a C8 run can still benefit during
its smaller-batch tail. Neither constant batch size nor split usage for every
request is implied by the client concurrency setting.

### Output agreement and limitations

All C1 trials were deterministic within each implementation (12/12 requests
matched that implementation's warmup output for each vector). However, old/new
C1 sequences first differ at zero-based output token **214, 6, and 42** for
the first three vectors. The 1528/32 vector matches all 32 tokens exactly.
The changed FP32 reduction order is a plausible source of these differences,
but no teacher-forced full-model logit comparison or independent quality corpus
was run to establish that attribution or quality equivalence. These throughput
results must not be presented as a bit-identical or quality-equivalent speedup
for the first three vectors.

The benchmark client's `--learn-expected` reference is a single-request output,
not an independent model oracle. In C8, the baseline already differs from this
reference for the first three vectors (0/24 exact matches each). The new path
has 0/24, 24/24, 24/24, and 24/24 matches respectively. This is an agreement
measurement, not evidence of improved model quality. No mismatch is hidden or
removed from the archived measurements.

## Exact final Qwen kernel

The final combined CUBIN, including the unchanged baseline entry point, was
also tested directly with the actual eight-token page geometry. The same
FP64 oracle, mixed-row preservation, empty-partition, KV-immutability and
deterministic cleanup checks pass. Maximum observed absolute error was
0.00024142. Compute Sanitizer memcheck reports **0 errors and 0 bytes leaked**;
stderr is empty. The oracle exercises the attention operator, not full-model
quality equivalence.

| Context / batch | Baseline µs | Compiler shared-KV split-8 µs | Speedup |
| --- | ---: | ---: | ---: |
| 59 / 1 | 14.34 | 24.52 | 0.58×; keep baseline |
| 128 / 1 | 26.33 | 24.65 | 1.07× |
| 256 / 1 | 49.39 | 26.61 | 1.86× |
| 512 / 1 | 95.07 | 32.45 | 2.93× |
| 1528 / 1 | 276.99 | 54.63 | 5.07× |
| 4096 / 1 | 735.75 | 114.53 | 6.42× |
| 1528 / 8 | 428.89 | 431.68 | 0.99×; keep baseline |

Kernel times are 200-iteration CUDA-event means, not serving measurements.
The initial register-only split experiment was rejected for runtime selection.
There are no performance records masquerading as measured autotune data: the
portable cost model chooses the grouped schedule, and the startup dispatch
uses a conservative measured crossover (context bucket ≥256, batch bucket ≤4).
